# 幹事操作說明

本文件寫給每星期實際操作「週報系統」的幹事看，**按實際的一星期工作
次序編寫**，不是按功能列表——照著標題順序看下去，就是幹事一星期會
遇到的事情次序。技術細節（工作表結構、程式架構）請見
[工作表結構.md](工作表結構.md)；系統整體介紹見
[系統總覽.md](系統總覽.md)。

---

## 星期一：系統自動寄出下主日週報

如果已經撳過選單「安裝自動寄送觸發器」，星期一（或 `Config` 設定的
其他日子）系統會**自動**：

1. 算出下一個主日，檢查職事表跟週報有沒有分歧，有的話寄一封提醒信
   給幹事（`Recipients` 的 `ADMIN` 組）；
2. 檢查有沒有新一季職事表已經生成、但季度填寫表還沒建立，有的話
   自動建立並寄出填寫邀請；
3. 組裝週報內容、產生 Word 附件、寄給堂委與執事——**除非
   `Config` 的 `DRY_RUN` 是 `TRUE`（系統預設），這一步只會在
   `SendLog` 留一筆記錄，不會真的寄出任何郵件**。

⚠️ **`DRY_RUN` 是全系統共用的一個開關**，不是「這一次操作要不要試行」
的選項。如果為了手動測試把它改成 `FALSE`，忘記改回 `TRUE`，下一次
自動觸發也會是真的寄送。建議養成習慣：測試完立刻改回 `TRUE`。

⚠️ Apps Script 的時間觸發器**只能指定「小時」，不能指定「分鐘」**，
而且**不保證準確在該小時執行**——實際觸發時間可能比預定時間晚數十
分鐘，甚至更久。這是 Google Apps Script 平台本身的限制，不是本系統
的 bug。

**幹事這一天要做的事**：如果收到「職事表分歧」提醒信，撳選單
「檢查職事表分歧」逐項確認要跟職事表還是保留週報自己的版本。如果
收到「季度填寫邀請」，代表新一季已經開始，見下面「每季一次」那一節。

## 平日：填寫本星期的內容

撳試算表選單「週報系統 ▸ 開啟填寫介面」，網頁介面填好本星期的崇拜
程序、人數、家事報告、代禱事項、團契、財政資料。每一格填完撳
「儲存」即可。事奉名單如果要臨時改動，同樣可以在這個介面直接
改——見下面「直接修改事奉名單」一節。

如果想一次過填完**整季**（例如領詩想一口氣填完一季的詩歌），改用
「季度填寫表」——一張表看晒整季每個主日，見
[季度填寫表使用說明.md](季度填寫表使用說明.md)。兩個介面改的是
**同一份資料**，哪一邊改了，另一邊下次開啟都會看到最新的值（靠系統
自動三方比對，見下面「名詞解釋」的「快照」）。

核對內容：撳選單「預覽週報郵件內容」，看看這一週的郵件會長什麼
樣——事奉框、程序表、人數表等有沒有明顯錯漏。這個動作**不會寄出任何
郵件**，可以隨時撳、撳幾次都沒關係。

### 浸禮三堂聯合崇拜那一週

浸禮合堂那一週，填寫介面會**多出一段「丙之二、浸禮合堂（副框）」**
（其餘主日這一段會自動隱藏，不用理會）。六格分兩類：

- **三個「主禮」**——每格**一位**，填姓名即可，系統會自動加尊稱
  （規則與事奉框完全一樣）。
- **三個名單欄**（受浸肢體／入會肢體／奉獻孩童）——可以填**多位**，
  用**空格分隔**。系統會**原樣印出**，不會自動加尊稱、不會重新排序，
  所以你怎樣排就怎樣印。

沒有的那一項**直接留空**就可以：

- 某一行兩格都留空 → 週報上**整行不會出現**（例如那期沒有孩童奉獻禮）。
- 六格全部留空 → 整個副框都不會出現。

⚠️ 隱藏了不等於清空——如果某一週本來是浸禮、後來改回平常主日，已經
填好的名單仍然保留在系統內，改返浸禮就會再看到。

## 產生週報 Word 檔、檢查、交付印刷

### 產生單一主日

選單「產生本週週報（Word）」，輸入主日日期，系統會產生一份 `.docx`
存到 `Config` 的 `BULLETIN_OUTPUT_FOLDER_ID` 指定的資料夾。用 Word
開啟檢查版面、內容都對，就可以直接交付印刷——**系統交付的是
`.docx`，不是 PDF**，理由與版面保留有關，見
[Word範本製作指引.md](Word範本製作指引.md) 檔頭的說明。

### 一次過產生整季

選單「產生本季全部週報（Word）」，輸入季度 ID（例如 `2027T4`），
系統會逐個主日產生 Word 檔，單一主日產生失敗不會中斷其餘的，最後
回報成功／失敗的數目，完整結果寫在 `Diagnostics` 工作表。

⚠️ 如果季度主日很多、執行時間接近 Apps Script 的 6 分鐘上限，系統
會**安全中止**並提示「已完成 N／M，請再撳一次繼續」——已經產生過的
主日不會重新做一次（用 `BulletinWeeks` 的 `LAST_GENERATED_AT` 判斷），
再撳一次選單就會接著做剩下的。

### 檢查

撳「檢查範本佔位符」，看看範本用到的佔位符系統有沒有全部提供、有
沒有疑似被 Word 拼寫檢查切斷的佔位符——**這一步應該在每次改動範本
之後都做一次**，不要等印出來才發現漏字。

---

## 每季一次：新一季開始的時候

1. **建立季度填寫表**：職事表那一季生成之後，撳「季度填寫表 ▸
   建立／刷新季度填寫表」，輸入季度 ID。這一步系統多數會自動幫你做
   （見上面「星期一」那一節），但也可以自己手動撳。
2. **寄出填寫邀請**：撳「季度填寫表 ▸ 寄出填寫邀請」，把季度填寫表
   的連結、待填統計寄給堂委、執事、IT、領詩、幹事（`Config` 的
   `FILL_INVITE_GROUPS` 可以調整名單）。
3. **產生本季團契**：撳「季度填寫表 ▸ 由常設時間表產生本季團契」，
   系統會依 `FellowshipDefaults` 的常設時間表自動補齊整季的團契聚會
   資料（已經存在的不會重複、也不會被覆蓋）。

💡 這三步都是**冪等**的——重複執行不會產生重複資料，也不會覆蓋人手
已經改過的內容。

### 想在新一季開始前，先看看整季會是什麼樣？

撳選單「全季流程演練」，輸入季度 ID。系統會**唯讀為主**地跑一次完整
流程（讀職事表快照、建立／刷新季度填寫表、產生團契、組裝每個主日的
週報資料模型、產生第一個主日的 Word 試看、組裝電郵內容但**不寄**、
檢查職事表分歧、統計待填欄位），把每一步的結果與耗時、全季總待填、
總警告、尊稱未設定人數、分歧衝突數，全部寫進 `Diagnostics`。

⚠️ 演練**不會寄出任何真郵件**（不論 `Config` 的 `DRY_RUN` 是什麼）；
但會產生一份**真實的** Word 檔（用來驗證整條產生鏈真的走得通），這份
檔案會留在輸出資料夾，需要人手清理。

## 出問題時去邊度看

系統有三張記錄工作表，加一份「完成度自我檢測」報告，出狀況時可以按
情況去查：

- **`SendLog`**：每一次寄送嘗試的記錄，一個收件人一行，可以看到
  「這封到底有沒有寄成功」「是不是試行」。
- **`ErrorLog`**：系統偵測到的例外狀況（例如收件人清單是空的、
  觸發器算出的日期不是星期日）。`SOURCE` 欄可以看出是伺服器、前端
  填寫介面，還是自動觸發器發生的問題。
- **`AuditLog`**：試算表本身的異動記錄，寄送成功時會在這裡看到
  `BulletinWeeks` 的狀態被改成 `SENT` 的那一筆。
- **`Diagnostics`**：每一次跑「檢查範本佔位符」「全季流程演練」
  「完成度自我檢測」「檢查職事表分歧」這類報告類選單，結果都會寫在
  這裡（每次覆蓋重寫，只留最新一次）。
- **Apps Script 專案的「執行項目」**：如果連 `ErrorLog` 都沒有記錄
  （例如整個腳本在載入階段就壞了），要去 Script Editor 的「執行項目」
  頁面看實際的例外堆疊。

**如果完全不確定系統現在狀態如何**，撳選單「完成度自我檢測」——這是
判斷「系統是否可以交付使用」的一站式報告，逐項列出設定、資料、功能、
記錄四大類的狀況，每項標 🟢（正常）／🟡（可運作但未完備）／🔴
（會令系統無法正常運作），對話框直接顯示三個數字的總計，完整清單寫進
`Diagnostics`。

如果「試寄下週週報」或自動寄送失敗，對話框（或 `ErrorLog`）通常會
講明原因，常見的幾種：

- **收件人清單是空的**：檢查 `Recipients` 工作表有沒有 `ACTIVE=TRUE`
  的行、`GROUP_NAME` 是不是在 `Config` 的 `SEND_GROUPS` 之內。
- **這個主日在職事表找不到資料**：確認職事表那一季已經生成、日期
  正確。
- **工作表結構落後於程式碼**：撳選單「初始化工作表」補齊。
- **範本檔案不是 Word 檔**：多數是 Google Drive 把上載的 `.docx`
  自動轉換成 Google 文件格式——去 Drive 設定關閉「將上載的檔案轉換為
  Google 文件編輯器格式」，重新上載原檔。
- **MailApp 每日配額不足**：Google 帳戶每天可以寄出的郵件數量有
  上限，配額用完要等隔天。
- **訊息內含「這是授權範圍問題」**：代表帳戶的授權令牌不包含這次
  操作需要的服務（例如第一次用到 Word 範本功能時才第一次用到
  `DriveApp`）。撳選單「檢查授權範圍」確認哪幾項未授權，再照對話框
  的指引重新授權——詳見
  [上線前檢查清單.md](上線前檢查清單.md)「第 0 步：確認授權範圍」。

## 選單項目一覽

試算表選單「週報系統」新增的項目（跟本文件相關的挑出來說明；其餘
項目屬於系統維護，一般操作用不到）：

| 選單項目 | 用途 | 會不會真的寄出郵件 |
|---|---|---|
| 開啟填寫介面 | 開啟網頁版填寫介面 | 不會 |
| 檢查職事表分歧 | 問一個主日日期，比對週報與職事表，結果寫入 `Diagnostics` | 不會 |
| 預覽週報郵件內容 | 問一個主日日期，顯示郵件內容 | **不會** |
| 試寄下週週報（依 DRY_RUN 設定） | 問一個主日日期，執行一次寄送流程 | **依 `DRY_RUN`** |
| 安裝自動寄送觸發器 | 設定每星期自動執行寄送 | 觸發時依 `DRY_RUN` |
| 移除自動寄送觸發器 | 取消每星期自動寄送 | 不會 |
| 查看觸發器狀態 | 列出目前安裝了哪些觸發器 | 不會（唯讀） |
| 產生本週週報（Word） | 問一個主日日期，產生 `.docx` 存到輸出資料夾 | 不會 |
| 產生本季全部週報（Word） | 問季度 ID，逐個主日產生 `.docx` | 不會 |
| 檢查範本佔位符 | 檢查三個 Word 範本的佔位符是否齊備 | 不會（唯讀） |
| 全季流程演練 | 問季度 ID，唯讀為主地跑一次完整流程並產生報告 | **不會**（強制不寄） |
| 完成度自我檢測 | 逐項檢測系統是否可以交付使用 | 不會（唯讀） |
| 本季待填清單 | 問季度 ID，把該季**完整**待填欄位明細寫入 `Diagnostics` | 不會（唯讀） |

## 直接修改事奉名單

填寫介面的「本週事奉」區塊可以**直接改**——每個崗位每個位次一個輸入
框，改完撳「儲存」即可。

⚠️ **在這裡改動的名單只存在週報，永遠不會寫回職事表。** 系統一格職事表
都不會寫。如果職事表本身要改，請自行到職事表更正。

幾個要知道的行為：

- **沒有改動過的崗位，會自動跟隨職事表最新版。** 職事表那邊改了人，
  週報下次載入就會跟著變，不需要你做任何事。
- **改動過的崗位，職事表之後再改也不會蓋過你的修改。** 系統只會把它
  標示為「衝突」，讓你自己決定要不要跟。
- 改動過的格子左邊會有一條**橙色直線**，旁邊有「還原」按鈕可以一鍵改回
  職事表的值；格子旁邊的灰色細字會顯示職事表現時的值。
- **衝突**的格子會用**紅底**，並同時列出三個值：你覆寫當時職事表是誰、
  職事表現在是誰、你的覆寫值是誰。
- 把輸入框**清空**，或者改回與職事表相同的值，就等於**取消覆寫**——
  那一格會改回跟隨職事表。（`DutyOverride` 工作表的記錄不會被刪除，
  只是標成無效，日後仍然查得到。）
- 覆寫的姓名如果對得上 `PersonDisplay` 的姓名，尊稱（弟兄／姊妹／
  牧師……）照樣會自動加上；對不上（例如臨時幫忙的訪客）就原樣顯示，
  這是正常的，不是錯誤。

## 自動寄送觸發器的細節

「安裝自動寄送觸發器」會依 `Config` 的 `SEND_WEEKDAY`（星期幾）與
`SEND_HOUR`（幾點，24 小時制）設定一個每週執行一次的時間觸發器。
重複安裝不會變成寄兩次——每次執行都會**先刪除全部既有的同名觸發器，
再建立一個新的**。

## 更新程式碼：`deploy.bat`（一鍵部署）

⚠️ 這一節是給**維護程式碼的人**看的，一般填寫週報用不到。

repo 根目錄有一個 `deploy.bat`，在 Windows 上雙撳（或者在命令列跑）
就會依次做完五件事，**任何一步失敗就立即停止並講明原因**：

| 步 | 做什麼 |
|---|---|
| 1 | `clasp push --force`　把 `src/` 推上 Apps Script |
| 2 | `git add -A` |
| 3 | `git commit`　（沒有任何改動就自動略過，不算失敗） |
| 4 | `git push`　推上 GitHub |
| 5 | `clasp deploy`　更新 Web App 部署 |

用法：

```
deploy.bat "這次改動的說明"
```

括號內那句會同時用作 commit 訊息與部署說明。不給參數的話會用預設訊息。

### 第一次用之前：建立 `deployment-id.txt`

`deploy.bat` **不會**把部署 ID 寫在檔案內（原始碼一律不放真實 ID）。
要在 repo 根目錄自己建立一個 `deployment-id.txt`：

- 內容：**一行**，只放 Web App 的部署 ID，不要加引號。
- 那個 ID 在 **Apps Script ▸ 部署 ▸ 管理部署作業** 取得。
- 這個檔案已經列入 `.gitignore`，**永遠不會被 commit 上 GitHub**。

檔案不存在時 `deploy.bat` 會直接停下來，並在畫面印出上面這段指示。

### 跑完之後仍然要人手做一件事

畫面最後會提醒：

```
仍需人手：試算表 ▸ 週報系統 ▸ 初始化工作表
```

**新增了 Config 設定鍵或者 `BulletinWeeks` 欄位之後，一定要撳一次**，
否則新欄位不會出現在試算表上。這個動作是冪等的（撳幾多次都一樣，
不會清走任何既有資料），不確定的時候撳多一次最穩陣。

## 名詞解釋

### `DRY_RUN`（試行模式）

`Config` 工作表的一個設定值，`TRUE` 或 `FALSE`：

- **`TRUE`（系統預設，建議平常保持這個值）**：執行寄送流程時，系統
  會做完全部檢查（收件人、內容、配額……），也會在 `SendLog` 留一筆
  記錄，但**完全不會呼叫寄信服務、不會有任何人收到郵件**。
- **`FALSE`**：寄送流程走到最後一步時**真的會寄出郵件**給每一位
  收件人。

`SendLog` 工作表的「是否試行」欄會清楚記下每一筆記錄是不是試行產生
的，方便事後查核。

### 衝突

**同一格內容，兩邊都被改過，系統不知道應該以哪一邊為準。** 有兩個
地方會出現「衝突」這個概念：

1. **週報覆寫 vs 職事表**：幹事在週報直接覆寫過某個崗位的人選，之後
   職事表那邊又改了同一個崗位——系統不會自動選邊，只會標示衝突，
   撳「由職事表重新取數」逐項確認。
2. **季度填寫表 vs 系統（`BulletinWeeks`）**：同一格在填寫表跟系統
   兩邊都被改過——撳「處理填寫表衝突」逐項選擇要用哪一邊的值。

兩種衝突的共同原則：**系統一格都不會自動改**，兩邊的值都完整保留，
一定要人手決定。

### 覆寫

幹事在週報（填寫介面或季度填寫表）直接改動某個崗位的事奉人選，跟
職事表當時的值不一樣，就叫「覆寫」。覆寫只影響週報顯示，**永遠不會
寫回職事表**；記錄在 `DutyOverride` 工作表，供日後查核與判斷是不是
衝突。

### 快照

系統用來判斷「自從上次一致之後，是哪一邊改過」的**基準值**——單純比較
「兩邊現在的值是不是一樣」是不夠的，因為兩邊不同可能代表「只有一邊
改過」（正常同步）或者「兩邊都改過」（衝突），沒有基準值分不出這兩種
情況。`FillSnapshot` 工作表存的就是季度填寫表與系統之間的快照；
`BulletinWeeks` 的 `ROSTER_SNAPSHOT_VERSION` 存的是週報與職事表之間
的快照（版本號形式）。快照由系統自動維護，人手不需要、也不應該直接
改動它。
