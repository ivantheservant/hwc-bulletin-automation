### 7-1. 為了做 Word 範本，放寬了「全 `src/` 不准用 `DriveApp`」這條 lint 規則

**背景**：`tools/lint-readonly-roster.js` 原本第 3 條規則是「全 `src/`
一律不准出現 `DriveApp`」，當時的註解寫明「日後真的需要才另外設計審查」。

prompt7 §4 明確要求 `readTemplateBlob_(fileId)` 用
`DriveApp.getFileById(fileId).getBlob()`，沒有 Drive 根本做不到。

**我的決定**：把規則 3 由「全面禁止」改成「**只准出現在
`src/DocxIo.gs`**」，手法跟既有的規則 1（`openById(` 只准出現在
`RosterRead.gs`）完全一樣——把能力鎖死在單一檔案，「有沒有人用 Drive
繞過職事表唯讀邊界」永遠只需要審一個檔案。

同時**新增規則 4**作為第二道防線：`DocxIo.gs` 內不准出現
`ROSTER_SPREADSHEET_ID`。理由是 `DriveApp.getFileById()` 理論上可以開啟
任何檔案（包括職事表本身），靜態上證明不了「某個執行期變數不是職事表
ID」，但可以證明「這個檔案從來拿不到職事表 ID 這個設定鍵」。

**要不要改**：如果 Ivan 覺得這個放寬不可接受，替代方案是由 Ivan 每次
人手把範本內容貼進試算表某一格（極不實際），或者改用 Apps Script 的
進階 Drive 服務（同樣要開權限，而且更難靜態稽核）。我認為目前的做法是
風險最低的一種。

⚠️ **日後任何人再想放寬這條規則，請先讀 `tools/lint-readonly-roster.js`
檔頭的完整說明。**

### 9-1. `Finance` 新增的 `COL5` 沒有對應的渲染佔位符

**背景**：prompt9 §1.6 原文同時出現兩個數字：「範本用了……`FINANCE`
清單的 `LABEL`、`COL1`、`COL2`、`COL3`、`COL4`（**五欄**）」（合計 5 個
渲染欄位），但緊接著又說「`Finance` 工作表現時只有
`COL_SPECIAL_OVERSEAS`、`COL_HARDSHIP` 兩欄。**加三欄** `COL3`、
`COL4`、`COL5`」（工作表變成 5 個數字欄）——兩句話對不上：如果渲染
只需要 4 個數字欄（`COL1`..`COL4`），工作表加 3 欄應該只到 `COL4`
就夠，不需要 `COL5`。

**我的決定**：兩邊都照字面實作——`Finance` 工作表加齊 `COL3`／
`COL4`／`COL5` 三欄（滿足「加三欄」），但渲染只接到 `COL1`..`COL4`
（滿足「五欄」＝`LABEL`＋4 個數字欄）。`COL5` 目前是**保留欄**，
資料存得進去，但不會出現在任何 Word 佔位符。

**理由**：兩種讀法都是對原文的合理詮釋，猜哪一種都有風險；照字面
兩句話分別實作，缺點只是多一個暫時用不到的欄位，不影響任何現有功能，
比起「猜錯而漏一個 Ivan 真正需要的渲染欄位」風險小得多。

**要不要改**：如果範本其實需要 `{{FINANCE.COL5}}`，只要在
`src/BulletinModel.gs` 的 `finance` 對應加一行 `col5: String(r.COL5 || '')`、
`src/BulletinRender.gs` 的 `buildRenderLists_()` 加 `COL5: renderValueText_(row.col5)`、
`supportedListPlaceholders_()` 的 `FINANCE` 欄位陣列加 `'COL5'`，三處
就補齊了。

### 9-2. `DUTY_PLACEHOLDER_MAX` 的預設上限（20）寫死在純函式層，不是即時讀 Config

**背景**：`buildRenderContext_()`（`src/BulletinRender.gs`）依專案既有
原則是**純函式**，不可以自己讀 `Config`——上限值要由呼叫方
（`generateBulletinDocx_()`）透過 `options.dutyPlaceholderMax` 傳進來。
但 `supportedValuePlaceholderNames_()`（「檢查範本佔位符」報告用來
列出「系統提供哪些佔位符」的函式）呼叫 `buildRenderContext_({}, {})`
時**沒有**傳這個選項，所以永遠用函式內建的預設值 20。

**我的決定**：不讓 `supportedValuePlaceholderNames_()` 讀 Config。

**理由**：這個函式目前完全不碰 `SpreadsheetApp`，`tests/bulletinrender.test.js`
整份測試檔案的 `GAS_STUBS` 是 `SpreadsheetApp: {}`（刻意留空，證明這一層
邏輯不依賴 Config）。改成讀 Config 會牽動這份測試既有的假設，而「系統
提供哪些佔位符」這份報告本來就是回答「系統認得哪些鍵」，不是「這星期
實際會填幾多格」——20 這個數字只是「系統支援的形狀」，跟 Ivan 有沒有把
`DUTY_PLACEHOLDER_MAX` 改成別的值是兩回事。

**代價**：如果 Ivan 把 `DUTY_PLACEHOLDER_MAX` 改成 30，「檢查範本佔位符」
報告的「系統提供」清單仍然只會列到 `DUTY_20`，範本如果用到
`{{DUTY_21}}`..`{{DUTY_30}}` 會被報成「範本用到但系統不提供」——但
**實際產生週報時**（`generateBulletinDocx_()` 走的是真正入口，會讀
Config 的實際值）那幾格照樣填得到，不受影響。這只是報告本身的一個
已知落差，不是功能性 bug。

**要不要改**：如果 Ivan 真的會調整這個上限，值得日後把
`inspectTemplatePlaceholders_()` 改成讀 Config 傳給
`supportedValuePlaceholderNames_()`（那個函式本身已經在 IO 層，改動
風險比動 `buildRenderContext_()` 小）。

### 9-6. 「週報輸出資料夾可寫入」的檢測，只驗證「開得到」，不是真正驗證「寫得進去」

**背景**：完成度自我檢測要求「`BULLETIN_OUTPUT_FOLDER_ID` 已設定且

**我的決定**：`checkOutputFolderAccessible_()`（`src/DocxIo.gs`）只
呼叫 `DriveApp.getFolderById(folderId)` 並讀它的名稱，開得到就算
通過。

**理由**：`DriveApp` 沒有直接的「這個帳戶對這個資料夾有沒有寫入權限」

`AuditLog`／Drive 活動記錄。
