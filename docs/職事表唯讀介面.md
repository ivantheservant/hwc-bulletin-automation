## 硬規則

1. **對職事表試算表一律唯讀，一個格都不可以寫。** 全 repo 只有
   `src/RosterRead.gs` 一個檔案可以出現 `openById(`，該檔案內不准出現
   任何寫入方法。由 `tools/lint-readonly-roster.js` 靜態掃描鎖住，
   commit 前要跑（見 [README.md](../README.md)）。
2. **不可以要求職事表系統改動任何一行程式碼。** 職事表的欄位結構照抄，
   有落差一律在週報這邊處理（例如把「聖餐襄禮」顯示成「聖餐輔禮」是
   `PostDisplay` 的事，跟這裡的讀取邏輯無關）。
3. **不可以寫死任何 ID。** 職事表試算表 ID 與六張工作表的名稱一律經
   `getConfig()` 讀取，Config 鍵見下表。
4. **缺失不可以靜靜當成正常值。** 見「錯誤處理契約」一節。
5. **不讀 `NameMapping` 的 `Email`／`Phone`／`PersonalLinkToken`。** 這三欄
   完全不會被讀進記憶體（`ROSTER_TABLE_DEFS_.NAME_MAPPING.columns` 只宣告
   `PersonID`／`NameTC`／`Active` 三欄）。

## 分層

```
┌─────────────────────────────────────────────────────────┐
│ readRosterSnapshot_(isoDate)          真正入口            │
│   ├─ 讀 Config（ROSTER_SPREADSHEET_ID／六個工作表名稱）    │
│   ├─ fetchRosterTablesCached_()       memoize 包裝        │
│   │    └─ fetchRosterTables_()        IO 層               │
│   │         └─ readRosterTable_()     單張表讀取＋型別正規化│
│   └─ buildRosterSnapshot_()           純函式層             │
└─────────────────────────────────────────────────────────┘
```

- **IO 層** `fetchRosterTables_(spreadsheetId, sheetNames)`
  全 repo 唯一會呼叫 `SpreadsheetApp.openById()` 的函式。把六張表各讀一次
  （`getRange().getValues()`），只讀白名單欄位，依欄位型別做**寬鬆**
  正規化（`rosterNormalizeByType_()`／`rosterToText_()` 等，**跟
  `src/SheetUtils.gs` 的 `normalize*_()` 完全分開，不共用**——見下面
  「為什麼對職事表用寬鬆解析」），回傳 `{ tables, warnings }`。**不做
  任何業務判斷**：不比對日期、不篩選版本、不解析特別主日、不查姓名
  對照。`warnings` 是讀取過程中遇到的、無法解析的整數／日期值。
- **純函式層** `buildRosterSnapshot_(tables, isoDate)`
  完全不碰 Apps Script 服務（不用 `SpreadsheetApp`／`Utilities`／
  `Session`），輸入是 IO 層的回傳值，做全部業務判斷，輸出快照物件。
  可以在 Node 用假 `tables` 直接測試，見 `tests/rostersnapshot.test.js`。
- **真正入口** `readRosterSnapshot_(isoDate)`
  先讀 Config；`ROSTER_SPREADSHEET_ID` 未設定就直接回傳
  `{ ok:false, notConfigured:true, ... }`，不呼叫 IO 層。否則呼叫 IO 層
  （同一次執行內 memoize，見下）取得 `{ tables, warnings }`，呼叫純函式層
  組出快照，再把 IO 層的 `warnings`（寬鬆解析時記錄的、無法解析的值）
  併入快照的 `warnings`。
- 另有 `listRosterServiceDatesForQuarter_(quarterId)`：列出指定季度的
  全部主日日期，供「測試讀取職事表（全季）」使用，跟
  `readRosterSnapshot_()` 共用同一份 memoized 資料。

### 效能與 memoize

`RosterAssignments` 可能有上萬行，六張表**各只讀一次**（一次
`getRange().getValues()`），不會針對個別崗位或個別主日重覆開表。
`fetchRosterTablesCached_()` 用 `spreadsheetId + JSON.stringify(sheetNames)`
當快取鍵，同一次執行（同一個 Apps Script 執行環境）內，第二次呼叫
`readRosterSnapshot_()` 不會重新讀試算表——這對「測試讀取職事表（全季）」
逐週呼叫尤其重要，一整季只會真正讀一次。

## 1. 職事表的資料結構——白名單欄位

職事表沿用與本專案相同的慣例：第 1 行中文標題、第 2 行機器鍵、資料由
第 3 行開始。讀取時一律用第 2 行機器鍵對照欄位位置（不是照固定欄數
讀）。

工作表名稱一律經 Config 讀取：

| Config 鍵 | 預設值 |
|---|---|
| `ROSTER_SHEET_ASSIGNMENTS` | `RosterAssignments` |
| `ROSTER_SHEET_VERSIONS` | `RosterVersions` |
| `ROSTER_SHEET_QUARTERS` | `Quarters` |
| `ROSTER_SHEET_SERVICE_DATES` | `ServiceDates` |
| `ROSTER_SHEET_NAME_MAPPING` | `NameMapping` |
| `ROSTER_SHEET_POSTS` | `Posts` |

`RosterRead.gs` 的 `ROSTER_TABLE_DEFS_` 對每張表宣告**白名單**——只列出
週報真正需要讀的機器鍵，與各自的型別（`TEXT`／`INT`／`DATE`／
`BOOLEAN`，見下面「為什麼對職事表用寬鬆解析」）：

| 工作表 | 白名單欄位（型別） |
|---|---|
| `RosterAssignments` | `QuarterID`(TEXT)／`VersionNo`(INT)／`ServiceDate`(DATE)／`PostID`(TEXT)／`SlotIndex`(INT)／`PersonID`(TEXT)／`PersonNameSnapshot`(TEXT)／`AssignSource`(TEXT)／`Locked`(BOOLEAN)；**選讀**：`RuleFlags`(TEXT) |
| `RosterVersions` | `QuarterID`(TEXT)／`VersionNo`(INT) |
| `Quarters` | `QuarterID`(TEXT)／`Stage`(TEXT) |
| `ServiceDates` | `ServiceDateID`(TEXT)／`QuarterID`(TEXT)／`ServiceDate`(DATE)／`WeekIndex`(INT)／`IsFirstSundayOfMonth`(BOOLEAN)／`ServiceType`(TEXT)／`SpecialID`(TEXT)；**選讀**：`Title`(TEXT) |
| `NameMapping` | `PersonID`(TEXT)／`NameTC`(TEXT)／`Active`(BOOLEAN) |
| `Posts` | `PostID`(TEXT)／`PostName_TC`(TEXT)／`SlotCount`(INT)／`Frequency`(TEXT)／`AutoGenerate`(BOOLEAN)／`DisplayOrder`(INT)／`Active`(BOOLEAN)／`EmptyDisplay`(TEXT) |

**選讀欄**（`optionalColumns`，2026-10-27）：職事表後來才加、舊試算表可能未有的欄。第 2 行找不到就當
每一行都是空值（TEXT＝`''`），**不拋錯、不記警告**。`ServiceDates.Title` 要等幹事第一次在職事表改
每週標題，職事表才會加這一欄。

⚠️ 2026-10-27 起**不再讀 `SpecialSundays`**（職事表第七十五輪起特別主日拿走，`SPECIAL_SUNDAYS_ENABLED`
預設 FALSE，那張表的內容不再影響職事表）。Config 舊鍵 `ROSTER_SHEET_SPECIAL_SUNDAYS` 已從程式拿走，
「初始化工作表」會列出來請人手確認後刪除。

**不在白名單內的欄，即使工作表裡有，也完全不會被讀取／正規化／驗證。**
對方（職事表系統）隨時可以新增其他欄位，或者把某個我們沒用到的欄位
改成別的型別，週報完全不受影響——這正是「不可以要求職事表系統改動
任何一行程式碼」這條硬規則的具體實作方式。

⚠️ `Quarters` 職事表原表還有 `Status` 欄位，但白名單刻意只列 `Stage`
（快照用的是 `Stage`，不是 `Status`）。`Stage` 的取值：`DRAFT` →
`REVIEW_SENT` → `REQUESTS_APPLIED` → `OFFICIAL_SENT`。只有
`OFFICIAL_SENT` 才代表該季職事表已經正式發出（`isOfficial`）。

⚠️ `RosterAssignments` 白名單**沒有** `ServiceDateID`——快照比對某個
主日的派工紀錄時，用 `QuarterID` ＋ `ServiceDate`（實際日期）配對，
不是用 ID 對照。

⚠️ `ServiceDates.SpecialID` 只作參考記錄（放在 `snapshot.serviceDate.specialId`），不用來查表。

⚠️ `NameMapping` **只讀** `PersonID`／`NameTC`／`Active` 三欄。
`Email`／`Phone`／`PersonalLinkToken` 等其餘欄位一律不讀進記憶體（硬規則）。

⚠️ `Posts` 白名單刻意**不列** `AllowConsecutive`：職事表的實際取值是
`ALLOW`／`BLOCK`／`WARN`（一個列舉），不是 boolean，週報也用不到——
第一版把它當 boolean 正規化，直接拋錯，詳見下面「為什麼對職事表用
寬鬆解析」與 `docs/已知bug類型.md`。

## 為什麼對職事表用寬鬆解析

### 兩種工作表要分開處理

- **自己的工作表**（週報試算表，`src/Constants.gs` 的 `COLUMNS`）：
  我們定義 schema，缺失或型別不符代表**我們自己**的 bug，應該立即拋錯。
  `SheetUtils.gs` 的 `normalize*_()` 系列就是為這種情境設計的。
- **別人的工作表**（職事表）：我們只是客人。硬規則
  「2026-12-04 之前不可以要求職事表改動任何一行程式碼」意味著職事表
  隨時會加欄、改列舉值，而我們沒有話事權。若沿用嚴格規則，對方加一欄
  或者某個欄位的取值超出我們的假設，我們就整個死掉——第一輪就是這樣
  中招：`Posts.AllowConsecutive` 的實際取值是 `ALLOW`／`BLOCK`／`WARN`，
  被當成 boolean 正規化，直接拋錯。

所以 `RosterRead.gs` 有自己一套**只給職事表用**的解析函式
（`rosterToText_()`／`rosterToIntLenient_()`／`rosterToDateLenient_()`／
`rosterIsTrueValue_()`），跟 `SheetUtils.gs` 的 `normalize*_()` **完全
分開，不共用**。這條界線很重要：**職事表的寬鬆解析函式不可以拿去用在
週報自己的工作表上，自己的表仍然要嚴格**——嚴格規則保護我們自己不會
悄悄壞掉，寬鬆規則保護我們不會因為別人的系統變動而死掉，兩者的用途
剛好相反，混用會兩邊都保護不到。

### 布林一定要與職事表的語意完全一致

職事表用的判斷是（`src/SheetReader.gs` 的 `isTrueValue_()`）：

```js
value === true || String(value).trim().toUpperCase() === 'TRUE'
```

空白、`FALSE`、任何其他值一律當 `false`，永不拋錯。`rosterIsTrueValue_()`
一字不差複製這個語意，**不可以自己另立一套**（例如接受 `是`／`1`／`Y`）。
兩邊語意不一致就會出現「職事表當它是關、週報當它是開」這種最難查的
問題——改 `rosterIsTrueValue_()` 之前，要先確認職事表 `isTrueValue_()`
那邊是不是也同步改了。

### 整數與日期也要寬鬆

- **整數**（`rosterToIntLenient_()`）：空白 → `null`（正常狀態，不記
  警告）；有值但解析不出來 → `null` 並記一筆 `ROSTER_VALUE_UNPARSEABLE`
  警告，**不拋錯**。
- **日期**（`rosterToDateLenient_()`）：接受 `Date` 物件與 `yyyy-MM-dd`
  字串；空白 → `null`；有值但解析不出來 → `null` 並記一筆
  `ROSTER_VALUE_UNPARSEABLE` 警告，**不拋錯**——該列在後續比對日期時，
  會因為這個欄位是 `null` 而自動配不到任何日期，等於被略過。

### 只有三種情況才拋錯

1. 工作表本身不存在。
2. 工作表第 2 行**缺少白名單內的機器鍵**（訊息列出缺哪幾個，以及是
   哪個 Config 鍵指向的哪張表）。
3. `openById()` 失敗（ID 錯／無權限）。

**多出來的欄位一律靜靜略過，不是錯誤。**

## 每週標題（2026-10-27 起取代「特別主日按日期比對」）

`buildRosterWeekTitle_(serviceDateRow)`：`ServiceDates.Title` 去頭尾空白之後有字，而且**不等於**
`ServiceType` ⇒ 這一週的標題，放在 `snapshot.special = { title, type: '', source: 'WEEK_TITLE' }`；
空白或等於 `ServiceType` ⇒ 普通主日（`special` 是 `null`）。沿用 `special.title` 這個位置，下游
（「特別主日：」一行、程序範本推斷、Word `{{SPECIAL_TYPE}}`、郵件標題、季度填寫表）不用改。

- 職事表的「類型」欄顯示 `Title || ServiceType`（`resolveWeekTypeText_()`）；幹事改回預設時它會清空

## 崗位 slot 的三種狀態

`buildRosterSlotIndex_(snapshot, communionWeeks, notApplicableRuleFlags)` 把派工紀錄整理成
`snapshot.slotsByPost`（`postId` → slot 陣列），每個 slot 都算好 `state`。
**`snapshot.posts` 列出的每一個啟用崗位都會有條目**——即使該崗位這一週
完全沒有派工紀錄，也會補一個空白 slot，好讓下游分得清「不適用」與「等人填」。

| state | 判斷條件 | 週報的處理 |
|---|---|---|
| `ASSIGNED` | 有人名（已去掉「不是人」的顯示字） | 正常顯示姓名 |
| `NOT_APPLICABLE` | `RuleFlags` 有 Config `ROSTER_NOT_APPLICABLE_RULE_FLAGS` 其中一個代號（預設 `HARD_COMMUNION_FIRST_SUNDAY`、`HARD_SPECIAL_SUNDAY_SKIP`）；或後備：`Posts.Frequency === 'FIRST_SUNDAY'` 而 `weekOfMonth` 不在 Config `COMMUNION_WEEKS` 內 | **整個崗位那一行不出現**（不是顯示「—」） |
| `PENDING` | 有這個 slot 但沒有人名，而且不屬於上面兩種（包括合堂那一週幹事在職事表清空的格：沒有 PersonID、名字和 RuleFlags） | 填寫介面顯示為空白並列入待填清單；印不印由 Config `DUTY_PRINT_EMPTY_ROWS` 決定（預設不印，見 `dutyRowsForPrint_()`）。不記警告 |

`EXTERNAL`（外判單位）2026-10-27 拿走：那是 `SpecialSundays.ExternalOwner` 的功能。

判斷次序**固定**是 `NOT_APPLICABLE` → `ASSIGNED` → `PENDING`，
理由見 `resolveRosterSlotState_()` 的 docstring 與 docs/已知bug類型.md
事故五：結構先於內容，而且要跟職事表的 `isStructuralNotApplicable_()`
同一個優先級。

`FIRST_SUNDAY` 這個字面值是**職事表的列舉值**（跟 `rosterIsTrueValue_()`
的布林語意一樣屬於「照抄對方實作」），所以放在程式碼；真正屬於我們的
規則是「首個主日是第幾週」，那一項在 Config 的 `COMMUNION_WEEKS`，由
`readRosterSnapshot_()` 讀好傳進純函式層。

## 2. `weekOfMonth`——自己算，不是抄 `WeekIndex`

`ServiceDates.WeekIndex` 是該季第幾週（1 到 13），**不是**週報需要的
「當月第幾個主日」。週報的兩條核心規則都靠後者：

- 聖餐在每月**第 1 個**主日（`Config` 的 `COMMUNION_WEEKS`）
- 「祈禱會」那一行只在每月**第 2 及第 4 個**主日出現
  （`Config` 的 `PRAYER_MEETING_WEEKS`）

所以一律由日期自己計算：

```
weekOfMonth = Math.floor((dayOfMonth - 1) / 7) + 1
```

`ServiceDates.IsFirstSundayOfMonth` 只作**交叉核對**：如果它是 `TRUE`
而算出來的 `weekOfMonth` 不是 1（或相反），會在 `warnings` 加一筆
`WEEK_OF_MONTH_MISMATCH`，但**不會**拋錯，也**不會**用職事表的值覆蓋
自己算的值。

## 3. 快照物件的形狀

`readRosterSnapshot_(isoDate)` 與 `buildRosterSnapshot_(tables, isoDate)`
一律回傳形狀完整的物件（就算 `notConfigured`／`found:false`，其餘欄位
也是 `null`／空陣列，不會整個省略），呼叫端不用逐層防呆：

```js
{
  ok: true,                    // 是否成功取得資料
  notConfigured: false,        // ROSTER_SPREADSHEET_ID 未設定時為 true，且 ok 為 false
  found: true,                 // 職事表內有沒有這個主日
  isoDate: '2027-10-03',
  weekOfMonth: 1,              // 自己算，不是抄 WeekIndex
  quarterId: '2027T4',
  quarterStage: 'DRAFT',       // Quarters.Stage 原值
  isOfficial: false,           // quarterStage === 'OFFICIAL_SENT'
  versionNo: 2,                // 該季 RosterVersions 的最大 VersionNo，沒有版本時是 null
  serviceDate: {
    serviceDateId: '...',
    weekIndex: 1,              // 職事表原值，只作參考
    isFirstSundayOfMonth: true,
    serviceType: '主日崇拜',
    specialId: '...',
    title: ''                  // ServiceDates.Title（選讀欄，沒有就是 ''）
  },
  special: null,                // 或者 { title: '三堂聯合崇拜', type: '', source: 'WEEK_TITLE' }
  assignments: [
    { postId: 'CHAIR', slotIndex: 1, personId: 'P9012', personName: '陳大文',
      assignSource: '...', locked: false, ruleFlags: [] }
  ],
  notAPersonTexts: ['（待填）', '—', ...],   // Config ROSTER_NOT_A_PERSON_TEXTS，下游比對用
  posts: [                     // Active=TRUE 的崗位，按 DisplayOrder 排序（跟主日日期無關）
    { postId: 'CHAIR', nameTC: '主席', slotCount: 1, frequency: 'WEEKLY',
      autoGenerate: true, displayOrder: 10, emptyDisplay: 'PENDING' }
  ],
  warnings: []                  // 每一筆是 { code, message }
}
```

### `warnings` 的 code 一覽

| code | 觸發時機 |
|---|---|
| `SERVICE_DATE_NOT_FOUND` | 該日期在 `ServiceDates` 找不到 |
| `WEEK_OF_MONTH_MISMATCH` | 自己算的 `weekOfMonth` 與 `IsFirstSundayOfMonth` 不一致 |
| `QUARTER_NOT_FOUND` | `ServiceDates` 指向的 `QuarterID` 在 `Quarters` 找不到定義 |
| `NO_VERSION_GENERATED` | 該季在 `RosterVersions` 沒有任何版本 |
| `NOT_OFFICIAL` | `Quarters.Stage` 不是 `OFFICIAL_SENT` |
| `PERSON_NOT_FOUND_IN_NAME_MAPPING` | `PersonID` 在 `NameMapping` 找不到 |
| `ROSTER_VALUE_UNPARSEABLE` | 白名單內的整數／日期欄位有值，但寬鬆解析仍然解析不出來（見「為什麼對職事表用寬鬆解析」） |

「不是人」的顯示字（職事表第八十二輪說明第 3.1 節；2026-10-27 起由 Config `ROSTER_NOT_A_PERSON_TEXTS`
決定，預設 `（待填）,⚠ 未能安排,—,特殊主日,待確認,另行安排,-,－,N/A,n/a`）：`PersonNameSnapshot` 去頭尾空白
之後與清單其中一項完全相同 ⇒ 當空白（未排定），**不記警告**——不印、不帶入獻花、不算「與職事表不同」
（舊覆寫的 `ROSTER_VALUE_AT_OVERRIDE` 比對時同樣當空白）。有 PersonID 一律用 `NameMapping.NameTC`。

沒有 PersonID 的名字（外請講員、臨時幫手）照顯示那個名字；尊稱改為**按名字**找 `PersonDisplay`
（與人手覆寫同一條路），找不到就照印、不記警告。

## 4. 錯誤處理契約

只有三種情況會拋錯（見「為什麼對職事表用寬鬆解析」的「只有三種情況才
拋錯」），其餘一律回傳形狀完整的快照物件並在 `warnings` 說明：

| 情況 | 行為 |
|---|---|
| `ROSTER_SPREADSHEET_ID` 是空字串 | 回傳 `{ ok:false, notConfigured:true, ... }`，**不拋錯**，也不當成「沒有資料」——呼叫端可以分辨「未設定」與「設定了但找不到」 |
| `openById()` 失敗（ID 錯／無權限） | **拋錯**，訊息含試算表 ID 前 8 個字元＋省略號（不印完整 ID）、原始錯誤訊息，以及「請檢查 Config 的 ROSTER_SPREADSHEET_ID，以及本帳戶是否有該檔案的檢視權限」 |
| 某張工作表不存在 | **拋錯**，訊息指明哪一個 Config 鍵指向的哪一個工作表名 |
| 工作表第 2 行找不到白名單內的**必要**機器鍵 | **拋錯**，列出缺少哪幾個鍵 |
| 工作表多出白名單以外的欄位 | **不拋錯**，靜靜略過，不讀、不驗證 |
| 白名單內的整數／日期欄位解析不出來 | 該欄位回 `null`，`warnings` 加 `ROSTER_VALUE_UNPARSEABLE`，**不拋錯** |
| `Posts.AllowConsecutive` 或任何列舉／非預期取值 | 因為根本不在白名單內，完全不會被讀到，也就不會出錯 |
| 該日期在 `ServiceDates` 找不到 | 回傳 `{ ok:true, found:false }`，`warnings` 加 `SERVICE_DATE_NOT_FOUND` |
| 該季在 `RosterVersions` 沒有任何版本 | 回傳 `{ ok:true, found:true, versionNo:null }`，`assignments` 空陣列，`warnings` 加 `NO_VERSION_GENERATED` |
| `Quarters.Stage` 不是 `OFFICIAL_SENT` | `isOfficial:false`，`warnings` 加 `NOT_OFFICIAL` |
| `PersonID` 在 `NameMapping` 找不到 | 用 `PersonNameSnapshot` 當 `personName`，`warnings` 加 `PERSON_NOT_FOUND_IN_NAME_MAPPING` |
| `PersonNameSnapshot` 是「不是人」的顯示字 | 當空白（未排定），不記警告 |
| 選讀欄（`Title`、`RuleFlags`）在工作表找不到 | 每一行當空值，不拋錯、不記警告 |
| `ServiceDates.Title` 空白或等於 `ServiceType` | `special` 為 `null`，不記警告——這一週就是普通主日 |
