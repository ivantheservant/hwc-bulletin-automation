# 職事表唯讀介面

本文件記錄週報系統讀取「粵語堂職事表」試算表的介面契約，對應
`src/RosterRead.gs`（IO 層＋純函式層＋真正入口）與
`src/RosterDiagnostics.gs`（選單用的測試報告）。如果程式與本文件有出入，
以 `src/RosterRead.gs` 為準，並請回頭修正本文件。

建立日期：2026-08-20（第二輪：職事表唯讀介面）

---

## 硬規則

1. **對職事表試算表一律唯讀，一個格都不可以寫。** 全 repo 只有
   `src/RosterRead.gs` 一個檔案可以出現 `openById(`，該檔案內不准出現
   任何寫入方法。由 `tools/lint-readonly-roster.js` 靜態掃描鎖住，
   commit 前要跑（見 [README.md](../README.md)）。
2. **不可以要求職事表系統改動任何一行程式碼。** 職事表的欄位結構照抄，
   有落差一律在週報這邊處理（例如把「聖餐襄禮」顯示成「聖餐輔禮」是
   `PostDisplay` 的事，跟這裡的讀取邏輯無關）。
3. **不可以寫死任何 ID。** 職事表試算表 ID 與七張工作表的名稱一律經
   `getConfig()` 讀取，Config 鍵見下表。
4. **缺失不可以靜靜當成正常值。** 見「錯誤處理契約」一節。
5. **不讀 `NameMapping` 的 `Email`／`Phone`／`PersonalLinkToken`。** 這三欄
   完全不會被讀進記憶體（`ROSTER_TABLE_DEFS_.NAME_MAPPING.columns` 只宣告
   `PersonID`／`NameTC`／`Active` 三欄）。

## 分層

```
┌─────────────────────────────────────────────────────────┐
│ readRosterSnapshot_(isoDate)          真正入口            │
│   ├─ 讀 Config（ROSTER_SPREADSHEET_ID／七個工作表名稱）    │
│   ├─ fetchRosterTablesCached_()       memoize 包裝        │
│   │    └─ fetchRosterTables_()        IO 層               │
│   │         └─ readRosterTable_()     單張表讀取＋型別正規化│
│   └─ buildRosterSnapshot_()           純函式層             │
└─────────────────────────────────────────────────────────┘
```

- **IO 層** `fetchRosterTables_(spreadsheetId, sheetNames)`
  全 repo 唯一會呼叫 `SpreadsheetApp.openById()` 的函式。把七張表各讀一次
  （`getRange().getValues()`），依欄位型別正規化（重用
  `src/SheetUtils.gs` 的 `normalizeByType_()`／`normalizeText_()` 等），
  回傳純陣列物件。**不做任何業務判斷**：不比對日期、不篩選版本、不解析
  特別主日、不查姓名對照。
- **純函式層** `buildRosterSnapshot_(tables, isoDate)`
  完全不碰 Apps Script 服務（不用 `SpreadsheetApp`／`Utilities`／
  `Session`），輸入是 IO 層的回傳值，做全部業務判斷，輸出快照物件。
  可以在 Node 用假 `tables` 直接測試，見 `tests/rostersnapshot.test.js`。
- **真正入口** `readRosterSnapshot_(isoDate)`
  先讀 Config；`ROSTER_SPREADSHEET_ID` 未設定就直接回傳
  `{ ok:false, notConfigured:true, ... }`，不呼叫 IO 層。否則呼叫 IO 層
  （同一次執行內 memoize，見下）再呼叫純函式層。
- 另有 `listRosterServiceDatesForQuarter_(quarterId)`：列出指定季度的
  全部主日日期，供「測試讀取職事表（全季）」使用，跟
  `readRosterSnapshot_()` 共用同一份 memoized 資料。

### 效能與 memoize

`RosterAssignments` 可能有上萬行，七張表**各只讀一次**（一次
`getRange().getValues()`），不會針對個別崗位或個別主日重覆開表。
`fetchRosterTablesCached_()` 用 `spreadsheetId + JSON.stringify(sheetNames)`
當快取鍵，同一次執行（同一個 Apps Script 執行環境）內，第二次呼叫
`readRosterSnapshot_()` 不會重新讀試算表——這對「測試讀取職事表（全季）」
逐週呼叫尤其重要，一整季只會真正讀一次。

## 1. 職事表的資料結構（照抄自職事表的 `src/Constants.gs`）

職事表沿用與本專案相同的慣例：第 1 行中文標題、第 2 行機器鍵、資料由
第 3 行開始。讀取時一律用第 2 行機器鍵對照欄位位置（不是照固定欄數
讀），所以工作表多出其他後加欄位不會造成任何問題；反過來，如果宣告
需要的機器鍵在第 2 行找不到，視為結構性問題，直接拋錯。

工作表名稱一律經 Config 讀取：

| Config 鍵 | 預設值 |
|---|---|
| `ROSTER_SHEET_ASSIGNMENTS` | `RosterAssignments` |
| `ROSTER_SHEET_VERSIONS` | `RosterVersions` |
| `ROSTER_SHEET_QUARTERS` | `Quarters` |
| `ROSTER_SHEET_SERVICE_DATES` | `ServiceDates` |
| `ROSTER_SHEET_SPECIAL_SUNDAYS` | `SpecialSundays` |
| `ROSTER_SHEET_NAME_MAPPING` | `NameMapping` |
| `ROSTER_SHEET_POSTS` | `Posts` |

`RosterRead.gs` 的 `ROSTER_TABLE_DEFS_` 對每張表宣告要讀哪些機器鍵、
各自的型別（`TEXT`／`DATE`／`BOOLEAN`／`INT`，跟 `Constants.gs` 的
`COLUMN_TYPES` 同一套）：

**`RosterAssignments`**：`AssignmentID`(TEXT)／`QuarterID`(TEXT)／
`VersionNo`(INT)／`ServiceDateID`(TEXT)／`ServiceDate`(DATE)／
`PostID`(TEXT)／`SlotIndex`(INT)／`PersonID`(TEXT)／
`PersonNameSnapshot`(TEXT)／`AssignSource`(TEXT)／`RuleFlags`(TEXT)／
`Locked`(BOOLEAN)／`UpdatedAt`(DATE)／`UpdatedBy`(TEXT)

**`RosterVersions`**：`VersionID`(TEXT)／`QuarterID`(TEXT)／
`VersionNo`(INT)／`SheetName`(TEXT)／`Basis`(TEXT)／
`ParentVersionNo`(INT)／`Status`(TEXT)／`Protected`(BOOLEAN)／
`WarningCount`(INT)／`CreatedAt`(DATE)／`CreatedBy`(TEXT)／`Notes`(TEXT)

**`Quarters`**：`QuarterID`(TEXT)／`Year`(INT)／`Term`(TEXT)／
`StartDate`(DATE)／`EndDate`(DATE)／`WeekCount`(INT)／
`GenerateOn`(DATE)／`OfficialSendOn`(DATE)／`Status`(TEXT)／
`Notes`(TEXT)／`Stage`(TEXT)／`StageUpdatedAt`(DATE)

⚠️ `Quarters` 同時有 `Status` 與 `Stage` 兩個欄位，**快照用的是
`Stage`**，不是 `Status`。`Stage` 的取值：`DRAFT` → `REVIEW_SENT` →
`REQUESTS_APPLIED` → `OFFICIAL_SENT`。只有 `OFFICIAL_SENT` 才代表該季
職事表已經正式發出（`isOfficial`）。

**`ServiceDates`**：`ServiceDateID`(TEXT)／`QuarterID`(TEXT)／
`ServiceDate`(DATE)／`WeekIndex`(INT)／`IsFirstSundayOfMonth`(BOOLEAN)／
`ServiceType`(TEXT)／`SpecialID`(TEXT)／`AutoGenerate`(BOOLEAN)／
`Notes`(TEXT)

**`SpecialSundays`**：`SpecialID`(TEXT)／`QuarterID`(TEXT)／
`ServiceDate`(DATE)／`Type`(TEXT)／`Title`(TEXT)／`SkipPostIDs`(TEXT)／
`LockPostIDs`(TEXT)／`ExternalOwner`(TEXT)／`CommunionOverride`(TEXT)／
`TranslationRequired`(BOOLEAN)／`Active`(BOOLEAN)／`Notes`(TEXT)
（此表可能還有其他後加欄位，讀取邏輯本來就容忍多出來的欄。）

**`NameMapping`**：**只讀** `PersonID`(TEXT)／`NameTC`(TEXT)／
`Active`(BOOLEAN) 三欄。`Email`／`Phone`／`PersonalLinkToken` 等其餘欄位
一律不讀進記憶體。

**`Posts`**：`PostID`(TEXT)／`PostName_TC`(TEXT)／`PostName_EN`(TEXT)／
`SlotCount`(INT)／`DistinctWithinPost`(BOOLEAN)／`Category`(TEXT)／
`Frequency`(TEXT)／`AutoGenerate`(BOOLEAN)／`AllowConsecutive`(BOOLEAN)／
`MutexGroup`(TEXT)／`DisplayOrder`(INT)／`Active`(BOOLEAN)／`Notes`(TEXT)／
`EmptyDisplay`(TEXT)／`EarlyArrivalMinutes`(INT)／`RequiredRoles`(TEXT)

## 2. `weekOfMonth`——自己算，不是抄 `WeekIndex`

`ServiceDates.WeekIndex` 是該季第幾週（1 到 13），**不是**週報需要的
「當月第幾個主日」。週報的兩條核心規則都靠後者：

- 聖餐在每月**第 1 個**主日（`Config` 的 `COMMUNION_WEEKS`）
- 「祈禱會」那一行只在每月**第 2 及第 4 個**主日出現
  （`Config` 的 `PRAYER_MEETING_WEEKS`）

所以一律由日期自己計算：

```
weekOfMonth = Math.floor((dayOfMonth - 1) / 7) + 1
```

`ServiceDates.IsFirstSundayOfMonth` 只作**交叉核對**：如果它是 `TRUE`
而算出來的 `weekOfMonth` 不是 1（或相反），會在 `warnings` 加一筆
`WEEK_OF_MONTH_MISMATCH`，但**不會**拋錯，也**不會**用職事表的值覆蓋
自己算的值。

## 3. 快照物件的形狀

`readRosterSnapshot_(isoDate)` 與 `buildRosterSnapshot_(tables, isoDate)`
一律回傳形狀完整的物件（就算 `notConfigured`／`found:false`，其餘欄位
也是 `null`／空陣列，不會整個省略），呼叫端不用逐層防呆：

```js
{
  ok: true,                    // 是否成功取得資料
  notConfigured: false,        // ROSTER_SPREADSHEET_ID 未設定時為 true，且 ok 為 false
  found: true,                 // 職事表內有沒有這個主日
  isoDate: '2027-10-03',
  weekOfMonth: 1,              // 自己算，不是抄 WeekIndex
  quarterId: '2027T4',
  quarterStage: 'DRAFT',       // Quarters.Stage 原值
  isOfficial: false,           // quarterStage === 'OFFICIAL_SENT'
  versionNo: 2,                // 該季 RosterVersions 的最大 VersionNo，沒有版本時是 null
  serviceDate: {
    serviceDateId: '...',
    weekIndex: 1,              // 職事表原值，只作參考
    isFirstSundayOfMonth: true,
    serviceType: '主日崇拜（十月主日（浸禮））',
    specialId: '...'
  },
  special: null,                // 或者下面的物件
  assignments: [
    { postId: 'CHAIR', slotIndex: 1, personId: 'P9012', personName: '陳大文',
      assignSource: '...', locked: false }
  ],
  posts: [                     // Active=TRUE 的崗位，按 DisplayOrder 排序（跟主日日期無關）
    { postId: 'CHAIR', nameTC: '主席', slotCount: 1, frequency: 'WEEKLY',
      autoGenerate: true, displayOrder: 10, emptyDisplay: 'PENDING' }
  ],
  warnings: []                  // 每一筆是 { code, message }
}
```

`special` 有值時（`ServiceDates.SpecialID` 有填，而且在 `SpecialSundays`
找得到對應的一行）：

```js
{
  specialId: '...', type: '...', title: '...',
  skipPostIds: ['USHER', 'COUNT'],       // 由逗號分隔字串解析成陣列（半形／全形逗號都支援）
  lockPostIds: [],
  externalOwner: '英語堂敬拜隊',
  communionOverride: '...',
  translationRequired: true
}
```

### `warnings` 的 code 一覽

| code | 觸發時機 |
|---|---|
| `SERVICE_DATE_NOT_FOUND` | 該日期在 `ServiceDates` 找不到 |
| `WEEK_OF_MONTH_MISMATCH` | 自己算的 `weekOfMonth` 與 `IsFirstSundayOfMonth` 不一致 |
| `QUARTER_NOT_FOUND` | `ServiceDates` 指向的 `QuarterID` 在 `Quarters` 找不到定義 |
| `NO_VERSION_GENERATED` | 該季在 `RosterVersions` 沒有任何版本 |
| `NOT_OFFICIAL` | `Quarters.Stage` 不是 `OFFICIAL_SENT` |
| `PERSON_NOT_FOUND_IN_NAME_MAPPING` | `PersonID` 在 `NameMapping` 找不到 |
| `PERSON_PLACEHOLDER` | `PersonNameSnapshot` 是佔位符（見下） |
| `SPECIAL_SUNDAY_NOT_FOUND` | `ServiceDates.SpecialID` 有填，但在 `SpecialSundays` 找不到對應的一行 |

`PersonNameSnapshot` 的已知佔位符：`—`、`待確認`、`⚠ 未能安排`
（`ROSTER_PERSON_PLACEHOLDER_SNAPSHOTS_`）。遇到這些值時，`personId`
一律設為 `null`（就算 `PersonID` 欄位剛好有值也一樣——佔位符代表「這個
崗位根本還沒排到人」，`PersonID` 不應該被信任），`personName` 照樣回傳
原值。

## 4. 錯誤處理契約

| 情況 | 行為 |
|---|---|
| `ROSTER_SPREADSHEET_ID` 是空字串 | 回傳 `{ ok:false, notConfigured:true, ... }`，**不拋錯**，也不當成「沒有資料」——呼叫端可以分辨「未設定」與「設定了但找不到」 |
| `openById()` 失敗（ID 錯／無權限） | **拋錯**，訊息含試算表 ID 前 8 個字元＋省略號（不印完整 ID）、原始錯誤訊息，以及「請檢查 Config 的 ROSTER_SPREADSHEET_ID，以及本帳戶是否有該檔案的檢視權限」 |
| 某張工作表不存在 | **拋錯**，訊息指明哪一個 Config 鍵指向的哪一個工作表名 |
| 工作表第 2 行找不到預期的機器鍵 | **拋錯**，列出缺少哪幾個鍵 |
| 該日期在 `ServiceDates` 找不到 | 回傳 `{ ok:true, found:false }`，`warnings` 加 `SERVICE_DATE_NOT_FOUND` |
| 該季在 `RosterVersions` 沒有任何版本 | 回傳 `{ ok:true, found:true, versionNo:null }`，`assignments` 空陣列，`warnings` 加 `NO_VERSION_GENERATED` |
| `Quarters.Stage` 不是 `OFFICIAL_SENT` | `isOfficial:false`，`warnings` 加 `NOT_OFFICIAL` |
| `PersonID` 在 `NameMapping` 找不到 | 用 `PersonNameSnapshot` 當 `personName`，`warnings` 加 `PERSON_NOT_FOUND_IN_NAME_MAPPING` |
| `PersonNameSnapshot` 是佔位符 | 照樣回傳原值，但 `personId` 設為 `null`，`warnings` 加 `PERSON_PLACEHOLDER` |

## 6. 靜態掃描 `tools/lint-readonly-roster.js`

commit 前要跑（見 [README.md](../README.md)）。三條規則：

1. `openById(` 只准出現在 `src/RosterRead.gs`。
2. `src/RosterRead.gs` 內不准出現任何寫入類方法（`setValue`／
   `setValues`／`appendRow`／`deleteRow`／`clear(`／`sort(` 等完整清單見
   該工具的原始碼）。`sort(` 有特別處理：JS 原生
   `Array.prototype.sort(比較函式)` 用來排序記憶體內的陣列（例如
   `posts` 按 `DisplayOrder` 排序）是安全、必要的操作，不算違規；只有
   `sort(` 後面**不是**接函式（例如 `range.sort(1)`）才會被判定為
   `Range.prototype.sort()`（Sheets 的列排序，是真正的寫入）而報錯。
3. 全 `src/` 不准出現 `DriveApp`（本輪完全不需要，出現即違規）。

對應的測試：`tests/lintreadonly.test.js`。
