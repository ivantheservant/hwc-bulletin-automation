## 二、改任何一行程式碼的完整循環

**永遠是這四步，缺一不可。**

### 第 1 步　用 Claude Code 寫，不要自己寫
你不用手寫程式。工作模式是：在對話裏講清楚要做什麼 → 我出一份
`prompt-xxx.md` → 你下載放進 repo 根目錄 → 在 Claude Code（Claude Desktop 的
Code 分頁）貼這句：

```
讀 prompt-xxx.md 並完全按照它執行。
中途不要停下來問我，有疑問寫入 docs/待確認事項.md，最後一併回報。
做完之後不要 git push，不要 clasp push，不要執行 deploy.bat，我自己跑。
```

Model 選擇：架構、schema、版面規則、難查的 bug → **Opus**；
其餘（電郵、觸發器、UI 小修）→ **Sonnet 5**。effort 一律 **High**。

### 第 2 步　推送（一個指令做完四件事）
```cmd
cd C:\HWC\SynologyDrive\Bulletin\claudecode\hwc-bulletin-automation
deploy.bat "這一次改了什麼"
```

`deploy.bat` 順序做：`clasp push --force` → `git add -A` → `git commit` →
`git push` → `clasp deploy -i <deployment-id.txt 內的 ID>`。
任何一步失敗即刻停低並顯示原因。

**跑完之後畫面會提你「仍需人手：初始化工作表」。**

### 第 3 步　初始化工作表
週報試算表 ▸ 選單 ▸ **初始化工作表**

新增了 Config 鍵或工作表欄位之後**一定要撳**。這一步是冪等的，撳多幾次無害。

### 第 4 步　驗證
選單 ▸ **完成度自我檢測**（快，30 秒）
選單 ▸ **跑自測**（慢，要撳幾次「繼續跑自測」）

- 週報資料模型：程序表條件、事奉框合併、誦讀按月輪替、祈禱會第 2、4 週、聖餐第 1 週

  家事報告與代禱事項有「連續到」可以一次過連登幾星期
- 內容表匯入：單向、先看差異再確認、逐格記 `AuditLog`、冪等
- 產生 Word：跨 run 佔位符處理、產出殘留實掃
- 發佈：固定 master 連結、版本、存檔副本、發佈前檢查、防重複、防揀錯檔案
- 電郵：`DRY_RUN` 保護、`SendLog` 記主旨與內文摘要
- 自測機四層：不變量、真環境自測 18 個情境、亂行機、產出實物斷言
- `deploy.bat` 一鍵部署

### 重要規矩（違反會出事）
1. **職事表一格都不可以寫**
2. **原始碼不可以寫死任何 ID、電郵、姓名、日期、行數**，一律經 `Config`
3. **不刪行**，只用 `ACTIVE=FALSE`
4. **工作表結構**：第 1 行中文標題、第 2 行機器鍵、第 3 行起是資料
5. `Diagnostics` 上限 380 行，每次執行清空重寫（所以跑自測會洗走自我檢測的報告）
6. `DRY_RUN` 平時保持 `TRUE`

### 已知 bug 類型（寫任何東西之前自問）
1. `.html` 註解裏不可以出現字面上的樣板標籤符號
2. 缺失被當成正常值靜靜過
3. 同一個狀態有兩個真相來源，只更新了其中一個
4. 由工作表讀出來的 Date／boolean 未經處理就用
5. 測試直接叫內部函式，沒有一個由真正入口叫下去
6. Shared Drive 上的 Drive 進階服務要 `supportsAllDrives`，否則 404
7. 前端沒有失敗處理，等於後端錯誤全部消失
8. 有副作用的檢查不可以當成不變量
9. 不變量假設了只有正式環境存在
10. 斷言指定了「用哪一道守門」，而不是「結果對不對」
11. 報告被自己的明細擠爆
12. 驗證函式與被驗證的邏輯用同一個假設，等於沒有驗證

## 七、人手測試清單（自測機做不到的）

**這些是真的有需要，不是為了幫你記起系統。** 自測機已經覆蓋的不會重複列出。

### 高優先（向堂委、執事簡報之前應該做）

**1. 內容填滿之後的版面（自測機用的是短樣本，測不到溢出）**
把一個主日照最近一期實際週報填滿：家事報告 4 條長文、代禱 5 條、財政全表、
團契 4 行、人數 12 格、獻花、講員講題。產生 Word，看：
- 是不是 4 頁（現在測試資料少，只有 3 頁）
- 有沒有變成 5 頁，或者第 4 頁尾被切走
- 表格有沒有跨頁斷開
這是你原本規格第 5 條「內容過多要自動處理」，至今從未真正驗過。

**2. 印出來對比現行印刷版**
A5 兩頁排一張 A4 雙面印。同一週的舊週報放旁邊比。看字級、框線粗幼、行距、
分頁位置。自測機只驗 XML 屬性，驗不到紙上的觀感。

**3. 星期一自動觸發器（R-028）**
自測機明確寫住它驗不到——因為那支函式會為真實季度建立填寫表，違反沙盒規則。
做法：把觸發時間暫時改成十分鐘後 → 等它自己跑 → 看 `SendLog` 與 `ErrorLog`
→ 改回星期一。

**4. master 連結在教會外面開得開**
用登出狀態的瀏覽器、用手機（iPhone 與 Android 各一）開 master 連結。
會眾不是教會網域內的人，這條路自測機驗不到。順便看 PDF 在手機上字型有無走樣。

**5. 兩個人同時改同一個主日**
兩個瀏覽器、兩個帳戶，同時開同一個主日、同時儲存。應該有一個被樂觀鎖擋住並
提示重新載入。自測機是單執行緒，驗不到。

### 中優先

**6. 由堂委角度填內容表**
找一位堂委實際填一次，特別看「連續到」是否好用、日期下拉是否夠清楚。
這是使用性問題，程式驗不到。

**7. 發佈錯了怎樣救**
故意發佈一份錯的，然後用 Drive 的版本記錄還原 master 檔案。

⚠️ 這一條之前做不到——`Drive.Revisions.list` 用了 v2 的欄位名，而進階服務
釘死在 v3，所以「讀不到版本記錄」。已經修好（見 docs/已知bug類型.md
事故三十七），並新增了一個選單。

**做法**：

1. 先發佈一份**正常**的（記低那一刻的時間）。
2. 再發佈一份**故意錯**的（例如上一期的 PDF）。
3. 選單 ▸ **發佈版本記錄（唯讀）** → 看 `Diagnostics`。
   應該列得出每一個版本的時間、位元組數、修改者，以及對照的 `PublishLog`
   紀錄。位元組數對得上哪一個版本，就是那一次發佈寫進去的內容。
4. 在 Drive 找到 master 檔案 → 按右鍵 ▸ **管理版本**。
5. 對照第 3 步的時間與位元組數，找出第 1 步那一版。
6. 按那一版右邊的三點 ▸ **下載**，先把它存到電腦。
7. 回到填寫介面，用「發佈及匯出」把剛才下載的那一份重新發佈。
8. 再撳一次「發佈版本記錄」，確認多了一版，而且 `PublishLog` 看得出
   還原這一次（版本號 +1）。

⚠️ **刻意沒有做「一鍵還原」**：還原等於再覆寫一次 master，而按錯的代價是
網站上那條固定連結指向錯的一期。多一步人手下載，是要你親眼看過那一份內容
才發佈。

⚠️ 還原**不是**把錯的那一版刪走，是再發佈多一版。所以 `PublishLog` 會有
三行（正常 → 錯 → 還原），日後查得出發生過什麼事。

做完之後在這裏記低實際步驟與撞到的問題。

**8. 真實寄給多過一個人**
`Recipients` 補齊之後（R-029），`DRY_RUN` 改 `FALSE`，寄一次給兩三個人，
確認每個人都收到、附件開得到、連結撳得開，然後**立即改回 `TRUE`**。
（單一收件人已經在 2026-08-20 驗過。）

### 不用做的

- 產生 Word 的正確性、佔位符殘留、匯入冪等、唯讀欄位擋、防重複、下一個主日的
  推算——自測機每次都跑，不用人手重複
- 職事表零寫入——有靜態 lint 加不變量，不用人手驗
